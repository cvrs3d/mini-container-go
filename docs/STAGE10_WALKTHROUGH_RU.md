# Stage 10 — разбор кода Mini Container

Этот документ объясняет подготовленный финальный код и тесты. Цель Stage 10 — не добавить «ещё одну фичу», а сделать уже работающий контейнер **проверяемым, читабельным и пригодным для портфолио**.

## Из чего состоит проект

- `main.go`: один Linux-специфичный исполняемый файл с CLI, namespaces, User Namespace, запуском systemd scopes, передачей сигналов и reaping.
- `main_test.go`: unit-тесты, которым **не нужен root**.
- `tests/smoke.sh`: отдельные интеграционные тесты для твоей Ubuntu VM с Alpine rootfs; специально запускаются через `sudo`.
- `README.md`: описание проекта, команды запуска, ограничения безопасности.
- `.github/workflows/ci.yml`: безопасные проверки на обычном GitHub runner; **не запускает привилегированный контейнер**.

## 1. `dispatch()` и `main()`

`dispatch(os.Args[1:])` разбирает первое слово CLI: `run`, `run-init`, `run-userns`, `run-limits`, и т. п. Он возвращает ошибку вместо того, чтобы вызывать `os.Exit` из середины кода. Это позволяет отдельно тестировать неверные аргументы.

`main()` — единственная точка, где вызывается `os.Exit(...)`.

`errorExitCode` различает обычные ошибки и ожидаемый ненулевой код дочерней программы. Например, если команда внутри контейнера выполнила `exit 42`, это **не системная ошибка runtime**: главное — завершиться с кодом 42, не печатая дважды `Error: exit status 42`.

## 2. `run()` — host parent

`exec.Command("/proc/self/exe", ... )` перезапускает тот же бинарник, но в режиме `child` или `child-init`. Три флага `CLONE_NEWPID | CLONE_NEWUTS | CLONE_NEWNS` создают отдельные PID, UTS и mount пространства имён. Это выполняется в **дочернем процессе**, а не в исходном хостовом процессе.

`cmd.Start()` и `cmd.Wait()` нужны раздельно, потому что между ними выполняется обработка сигналов.

Канал `sigCh` получает `SIGTERM`/`SIGINT` от хоста. Goroutine перенаправляет сигнал к PID 1 контейнера. Если контейнер не завершится за три секунды, выполняется `Kill()`.

`done` и `forwarderDone` позволяют основной goroutine завершить сигнал-обработчик аккуратно и избежать утечек/гонок.

## 3. `child()` — подготовка окружения

`child()` выполняется уже в новых namespaces, поэтому:

1. `MS_PRIVATE|MS_REC` отключает propagating mounts обратно к хосту.
2. `Chroot(rootfs)` и `Chdir("/")` переключают видимую корневую директорию на Alpine.
3. `Mount(proc, /proc)` даёт корректные данные о PID в новом namespace.
4. `Mount(tmpfs, /tmp)` создаёт отдельное временное хранилище.
5. `Mount(tmpfs, /dev)` создаёт отдельный каталог устройств.
6. `Mknod(/dev/null, S_IFCHR|0666, 1:3)` создаёт устройство Linux `/dev/null`, **только в привилегированном режиме**.

В Stage 10 внешняя библиотека `golang.org/x/sys/unix` больше не нужна для единственной операции `Mkdev(1,3)`: в нашем учебном Linux-only runtime установлен `linuxDevNull = (1 << 8) | 3`. Это encoded `dev_t` для major 1/minor 3. Для произвольных устройств лучше использовать общую Linux-функцию `makedev`, а не хардкодить значения.

`run` вызывает `syscall.Exec()` и заменяет Go-процесс приложением. `run-init` вызывает `runInit()` — тогда Go остаётся PID 1.

## 4. `runInit()` — собственный init и reaper

**Зачем:** программы внутри контейнера могут запускать фоновые процессы. Когда промежуточный родитель завершается, осиротевшие процессы становятся детьми PID 1. Без `wait` они могут оставаться zombie.

`signal.Notify` получает `SIGCHLD`, `SIGTERM`, `SIGINT`.

`syscall.ForkExec()` запускает основную программу и возвращает её PID. Мы сознательно **не используем `cmd.Wait()`**, иначе он конкурировал бы с `wait4(-1)` за статусы процессов.

`reapExitedChildren(mainPID)` вызывает `wait4(-1, WNOHANG)` в цикле:

- `pid > 0`: собрали завершившегося ребёнка; если это `mainPID`, запоминаем его статус.
- `pid == 0`: все уже завершившиеся дети собраны, оставшиеся ещё работают.
- `ECHILD`: больше нет детей для ожидания.
- `EINTR`: повторяем прерванный системный вызов.

**Почему цикл:** несколько завершений могут породить только одно доставленное уведомление SIGCHLD. Один `wait4()` собирает не более одного процесса.

Если пришёл TERM/INT, Go Init выполняет `syscall.Kill(mainPID, signal)`. Не рассчитывай, что отправка сигнала PID 1 сама по себе доставит его дочерним процессам — сигналы не распространяются автоматически по дереву.

Когда **главная** программа завершилась, init сохраняет её код. Это не full production supervisor: живые потомки при завершении PID 1 будут остановлены ядром PID Namespace.

## 5. `parseHostIDs()` и `userNSAttributes()`

Исходный код дважды читал `SUDO_UID` и `SUDO_GID`. Теперь есть один валидатор `parseHostIDs()` и один конструктор `SysProcAttr`.

`UidMappings: [{ContainerID: 0, HostID: 1000, Size: 1}]` задаёт перевод идентификаторов. `Credential{Uid:0}` задаёт идентификатор процесса **внутри** namespace. Это разные действия.

Этот путь **не rootless**: на твоей VM при обычном пользователе настройка mapping блокировалась политикой безопасности Ubuntu. Мы не меняем AppArmor и не обходим эти ограничения.

## 6. `parseLimits()`, `buildScopeArgs()`, `runScope()`

`parseLimits()` отделяет флаги (`--memory` и `--cpu`) от пользовательской команды `fs.Args()` и проверяет значения. Благодаря этому параметры можно тестировать обычным `go test`.

`buildScopeArgs()` строит список аргументов вида:

```
systemd-run --scope --same-dir --expand-environment=no \
  --property=MemoryMax=256M --property=CPUQuota=50% \
  /home/dev/projects/mini-container-go/mini-container run /bin/sh
```

Важно, что запускается **`mini-container run /bin/sh`**, а не просто `/bin/sh` на хосте. В `exec.Command` аргументы передаются отдельными строками, поэтому не нужно самостоятельно экранировать shell-выражения.

`MemoryMax` и `CPUQuota` применяются ко всем процессам cgroup. `CPUQuota=50%` означает в среднем 0.5 логического CPU по суммарному времени, а не привязку к половине физического ядра.

## 7. Unit vs. integration vs. CI

`main_test.go` проверяет чистую логику без root: парсер, генерацию аргументов, mappings и exit code. Это быстрые тесты, которые должны запускаться при каждом изменении.

`tests/smoke.sh` проверяет реальное поведение Linux: PID 1, Alpine rootfs, виртуальные ФС, устройства, сигналы, reaping и (опционально) cgroups v2. Его запуск требует `sudo` и доверенной VM. Это **не** задача для публичного CI runner.

CI запускает только непривилегированные unit tests, race detector, vet и cross-build под ARM64. Так мы не даём GitHub runner прав на host namespaces/mounts.

## 8. Что выполнить на своей VM

Рекомендуемый порядок:

```bash
cd ~/projects/mini-container-go
cp main.go main.go.before-stage10
# Разверни содержимое ZIP поверх своего проекта; rootfs/ не трогай.

gofmt -w main.go main_test.go
go test ./...
go test -race ./...
go vet ./...
go build -o mini-container .

sudo ./tests/smoke.sh
sudo env RUN_CGROUP_TEST=1 ./tests/smoke.sh
```

`go test` и Linux ARM64 сборка уже были проверены в среде подготовки файлов. Реальные privileged smoke-тесты необходимо запустить на твоей VM: в текущей среде нет твоего Alpine rootfs, разрешений на namespace/mount operations и systemd scopes.

## 9. Что намеренно осталось за рамками

Это учебный project, не safe sandbox. Нет seccomp, ограничений capabilities, отдельной сети, cgroup delegation для rootless, read-only rootfs, полноценного `/dev`, общей пересылки сигналов всей группе процессов, OCI image формата и надёжного процесса cleanup для произвольных отказов.

Эти недостатки нужно честно указать в README и на собеседовании, а не скрывать.
